# EvoZeus-CoEvolve v0.15.0

v0.15.0 将目标 Repo 内的 Harness 规则收敛到 canonical Harness Skill v1.1，并为 v0.14 目标提供可审查、可批准、可验证回滚的迁移路径。普通聊天中的 Lesson 触发由 EvoZeus Core runtime 执行，CoEvolve 负责受控注册与依赖校验。

## 从 v0.14 到 v0.15

- 每个目标 Repo 继续只维护一个根级 Evolution Harness；目标 Skillware 的业务版本保持独立。
- canonical Harness Skill 固定在 `.evozeus-wrapper/skills/using-evozeus-harness/SKILL.md`，其独立契约版本为 `v1.1.0`。
- 目标业务入口只保留一段紧凑 activation block。Harness 的运行检查、Feedback Issue、Issue-to-PR、维护、UAT、Release 与 rollback 规则统一由 canonical Harness Skill 提供。
- v0.15.0 成为新接入目标的默认 Harness 基线。
- 历史目标通过版本化 migration profile 到达 v1.1 closure；发布谱系与本次实际迁移谱系分别记录，方便审查和追溯。

## 普通聊天 Lesson runtime 依赖

普通聊天中的 Lesson 检测依赖 EvoZeus Core 提供的 `evozeus.user-prompt.lesson-runtime.v1` API。v0.15.0 的依赖契约绑定 EvoZeus Core PR [#50](https://github.com/MetaInFLow/EvoZeus/pull/50) 与源修订 `4dc94613ee01c6bd3c7fa8f5f123c6fe398742f4`；该组件在本 release 准备时仍标记为 `unreleased`。

CoEvolve 只管理 `SessionStart` / `UserPromptSubmit` 注册、信任状态、刷新、卸载和目标指针生命周期。Core 负责读取事件、选择目标与执行 Lesson runtime。安装或刷新前，CoEvolve 会核对 active product manifest、Core dispatcher bytes、runtime API 和 HOME 路径边界；依赖缺失或不兼容时停止安装且不写入注册。

用户应先安装包含上述 API 的受信 EvoZeus Core 版本，再启用 CoEvolve 的全局 Lesson lifecycle。canonical Harness Skill 的目标 Repo 治理能力不依赖 CoEvolve 自行复制 Core runtime。

## 升级与迁移

开始前确认以下条件：

- EvoZeus-CoEvolve `v0.15.0` 已作为官方 release 发布，当前 source checkout、release tag 与官方 remote tag 指向同一 Commit。
- 目标位于独立 Git Repo，工作区干净且 `origin` 与目标 GitHub Repo 匹配。
- 执行账号对目标 Repo 具有 GitHub `ADMIN` 权限。

先为单个目标生成只读计划：

```text
python3 scripts/evozeus_wrapper.py harness migrate-layout \
  --target /absolute/path/to/repo \
  --latest-version v0.15.0 \
  --dry-run \
  --json
```

计划结果按证据分流：

- `supervised_migration_available`：仅适用于完整匹配已审查 v0.14 三段式布局的目标，批准值取 `operation_sha256`。
- `automatic_migration_available`：仅适用于完整匹配 canonical v1.0 closure 的目标，批准值取 `plan_sha256`。
- `manual_migration_required`：证据不完整、布局歧义或受保护内容不匹配，保持 `writes=false`，进入人工审查。

审查计划中的 write / delete / move 集合、受保护业务内容和 rollback 信息后，提交同一份 exact digest：

```text
python3 scripts/evozeus_wrapper.py harness migrate-layout \
  --target /absolute/path/to/repo \
  --latest-version v0.15.0 \
  --approve-plan 'sha256:<operation_sha256-or-plan_sha256>' \
  --json
```

批量升级同样先计划，再批准本次 `batch_plan_sha256`：

```text
python3 scripts/evozeus_wrapper.py harness upgrade-all \
  --latest-version v0.15.0 \
  --dry-run \
  --json

python3 scripts/evozeus_wrapper.py harness upgrade-all \
  --latest-version v0.15.0 \
  --approve \
  --approve-plan 'sha256:<exact-batch-plan-digest>' \
  --json
```

任何重新规划导致的 digest 变化都会阻断写入。每个目标仍需分别通过权限、Git 状态、路径和 postcondition 校验。

## Rollback

每次 apply 会在目标 Repo 外创建 receipt-bound 完整 snapshot，并在返回结果中给出 snapshot 路径。apply 中途失败时，迁移器先恢复 snapshot 并验证 preimage；需要人工恢复时执行：

```text
python3 scripts/evozeus_wrapper.py harness rollback-migration \
  --target /absolute/path/to/repo \
  --snapshot /absolute/path/to/trusted-snapshot \
  --approve \
  --json
```

rollback 在首个恢复写入前验证 transaction、plan digest、snapshot descriptor、全部备份 hash、路径类型和目标当前状态。恢复完成后再处理 Git commit revert 或后续维护提交。

## 安全边界

- 历史 heading、frontmatter、regex、旧路径和 terminal signature 只用于发现候选，不能授权写入。
- destructive apply 只接受 release-bound profile、完整 exact preimage、一次性 exact plan approval 和干净目标工作区。
- 所有写入同时校验内容 hash、Git mode、路径 containment、symlink、path traversal、manifest 身份与受保护业务内容。
- 迁移后的 structure 校验只执行官方 release closure 中已验证的 preflight 与 Notice 源码；目标 Repo 自带的未验证 Python 不进入该信任链。
- 普通 Skill 调用只执行只读运行检查，不授予 Harness 维护、Issue、分支、PR、UAT、Release 或 rollback 权限。
- CoEvolve 不读取普通聊天 prompt、不选择 Lesson 目标、不执行 Session Signal，也不接管 EvoZeus Core 的产品传输。
- 发布 workflow 在 ruleset、branch protection、release environment 与 immutable-release 控制未通过时保持 fail-closed。

## 验证范围

v0.15.0 的回归覆盖 fresh attach、canonical v1.0 自动升级、reviewed v0.14 supervised migration、LF/CRLF apply-and-rollback、歧义零写入、plan 重放拒绝、snapshot 篡改、路径与 symlink 攻击、Core runtime 缺失或不兼容，以及第三方 Hook 保留。
